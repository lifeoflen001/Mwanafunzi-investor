# Mwanafunzi Investor — Hosting & Deployment Guide

This guide is for the Laravel application in this repository. It covers the public website, student portal, admin CMS, commerce records, public media, queued commerce mail, SEO routes and the production asset build.

## Production Readiness Status

The repository is ready to deploy to a compatible Laravel host. The remaining items are server-owned configuration, not code blockers:

| Area | Status |
| --- | --- |
| Application code | READY |
| Database migrations | READY; run them on the target database |
| Frontend build | READY; `public/build/manifest.json` is generated by `npm run build` |
| Laravel cache build | READY; config, route and view caches build successfully |
| Storage/media code | READY; the public storage link is required on the host |
| Security defaults | READY; production must set `APP_DEBUG=false` and a real `APP_KEY` |

## 1. Application Overview

- Framework: Laravel 12 (`composer.json` requires `laravel/framework ^12.0`; the audited install reports Laravel 12.69.2).
- PHP: 8.2 or newer within the supported Laravel/PHP range. PHP 8.2 is the minimum declared by Composer.
- Database: MySQL or MariaDB in production. The application also supports SQLite for automated tests.
- Frontend: Vite 7 with Laravel Vite Plugin and Tailwind CSS. Build assets with Node before deployment; production PHP does not need Node after `public/build` is uploaded.
- Web server: Apache with `mod_rewrite` or Nginx configured to send non-file requests to `public/index.php`.
- Storage: public media is written to the `public` disk (`storage/app/public`) and served through the `public/storage` link. Private commerce files use the local/private disk.
- Queue: database queue by default. Queued `CommerceMail` messages require a worker or a cPanel cron worker.
- Scheduler: no `routes/console.php` scheduled task is currently registered, so a scheduler cron is not required for this release.

## 2. Server Requirements

### PHP and extensions

Install PHP 8.2+ with these extensions available to the web SAPI and CLI SAPI:

- PDO and `pdo_mysql` for MySQL/MariaDB
- `fileinfo`
- `openssl`
- `json`
- `mbstring`
- `ctype`
- `tokenizer`
- `xml`, `dom`, and `xmlwriter`
- `session`
- `filter` and `hash`
- `curl` for reliable HTTP calls to the Flutterwave API when live payments are enabled

GD is strongly recommended for responsive WebP variants. It is optional: the media service keeps the original image when GD/ImageMagick is unavailable, but responsive variants will not be generated. Imagick can be used by the host as an alternative image-processing capability if the host supports it; the application does not require both GD and Imagick.

Composer verifies the Laravel runtime requirements. `composer check-platform-reqs` was successful in the audited environment.

### Database and tools

- MySQL 8+ or MariaDB 10.5+ is recommended.
- Composer 2 is required for dependency installation.
- Node.js 20.19+ or 22.12+ is required only to build the Vite assets. The lockfile's Vite toolchain requires a current Node release.
- The production server needs enough disk for the application, `vendor/`, `public/build/`, logs, database cache/session/job rows and uploaded media. Plan capacity from actual media growth rather than relying on a fixed minimum.
- `storage/` and `bootstrap/cache/` must be writable by the web/PHP user. Use the host's ownership model and normally `775` where appropriate; do not use `777` as the standard solution.

## 3. Shared Hosting / cPanel Deployment

The safest layout keeps the Laravel application outside the public web directory:

```text
/home/USERNAME/mwanafunzi/
    app/
    bootstrap/
    config/
    database/
    public/
    resources/
    routes/
    storage/
    vendor/
    .env
    artisan

/home/USERNAME/public_html/
    index.php
    build/
    images/
    favicon.svg
    favicon.ico
    storage -> /home/USERNAME/mwanafunzi/storage/app/public
    .htaccess
```

Prefer the application directory and the domain document root configuration described below. Do not expose `app/`, `config/`, `database/`, `resources/`, `routes/`, `storage/`, `.env` or `vendor/` as directly browsable public directories.

### Preferred document-root configuration

If cPanel allows the domain or subdomain document root to point directly to the project, use:

```text
/home/USERNAME/mwanafunzi/public
```

This is the preferred configuration. It preserves the repository's normal Laravel paths and requires no manual `public/index.php` path edits.

### Separate `public_html` configuration

If the host requires `public_html`:

1. Upload the application to `/home/USERNAME/mwanafunzi/` outside `public_html`.
2. Upload the contents of the repository's `public/` directory into `public_html/`, including `build/`, `images/`, `favicon.svg`, `favicon.ico` and `.htaccess`.
3. Do not upload the repository root `.env` to a public directory.
4. Edit only the copied `public_html/index.php` paths, based on the actual account path. The repository version assumes the normal layout and contains:

   ```php
   require __DIR__.'/../vendor/autoload.php';
   $app = require_once __DIR__.'/../bootstrap/app.php';
   ```

   With the separated layout, these become paths such as:

   ```php
   require '/home/USERNAME/mwanafunzi/vendor/autoload.php';
   $app = require_once '/home/USERNAME/mwanafunzi/bootstrap/app.php';
   ```

   Keep the maintenance-file path aligned with the application directory as well. Do not paste these paths without replacing `USERNAME` with the real account path.
5. Ensure `public_html/.htaccess` is the repository's Laravel public `.htaccess`.
6. Create `public_html/storage` as a symbolic link to `/home/USERNAME/mwanafunzi/storage/app/public`, or ask the host to create the equivalent web-server alias.
7. Copy the built `public/build/` directory into `public_html/build/`.

The `asset()` URLs produced by this application expect `/build/...`, `/images/...` and `/storage/...` to be under the domain document root.

Production must use:

## 5. Database Setup and Safety

### New server database

1. Create a MySQL/MariaDB database in cPanel.
2. Create a database user with a strong password.
3. Grant that user privileges on only this database.
4. Enter the real values in the server `.env`.
5. Test the connection with `php artisan about` or `php artisan migrate:status`.
6. Run the incremental migrations:

   ```bash
   php artisan migrate --force
   ```

Never use `php artisan migrate:fresh`, `php artisan db:wipe` or a table reset on a populated server.

### Migrations

The repository migrations are incremental. They create the users, sessions, cache/jobs, platform, commerce, CMS, portfolio and runtime-index tables in sequence. Foreign keys use explicit cascade/null-on-delete behavior, and the latest runtime-index migration is additive.

The `down()` methods exist for development/package lifecycle use; they are not a live rollback strategy. Before any major migration, back up the database and review the migration SQL. Do not casually roll back a live database after users, orders, payments or media references exist.

### Seeders

Do not run `php artisan db:seed` blindly on a live database. `DatabaseSeeder` creates the initial editorial/content baseline. It now skips the local `test@example.com` demo account when `APP_ENV=production`, but it can still update starter content. On a brand-new installation, run it only after confirming that the starter content is wanted:

```bash
php artisan db:seed --class=DatabaseSeeder --force
```

For an existing live installation, use migrations and the admin CMS instead. Create the first real administrator with the password-prompting command:

```bash
php artisan app:make-admin YOUR_ADMIN_EMAIL --name="Your Name"
```

Do not pass a password in shell history unless the hosting policy explicitly allows it.

## 6. Composer Deployment

Preferred server command:

```bash
composer install --no-dev --prefer-dist --optimize-autoloader
```

The application runtime does not require development dependencies. Keep `composer.lock` with the deployment so the server installs the audited dependency versions.

If the host has no Composer/SSH access, run the same command locally in a matching PHP 8.2+ Linux-compatible environment, upload the resulting `vendor/` directory with the application, and do not commit `vendor/` to Git. Rebuild it whenever `composer.lock` changes.

## 7. Frontend Build and Vite Manifest

Build before deployment:

```bash
npm ci
npm run build
```

`npm install` may be used when there is no lockfile, but this repository includes `package-lock.json`, so `npm ci` is preferred. The build writes:

```text
public/build/manifest.json
public/build/assets/...
```

Upload `public/build/` to the live document root. The live application does not need `npm run dev` or a Node process after those assets are built. A missing manifest means the build directory was not uploaded or the document root is pointing at the wrong `public` directory.

The audited production build generated approximately 177.55 kB CSS (32.17 kB gzip) and 68.76 kB JavaScript (24.61 kB gzip). Build output is ignored by Git, so it must be generated during deployment or included in the release package.

## 8. Storage, Uploads and Permissions

Run from the application directory:

```bash
php artisan storage:link
```

The link must expose:

```text
public/storage -> storage/app/public
```

The application uses public media for logos, hero images, project galleries and testimonial media. Private commerce assets are stored outside the public media directory and are served through signed, authorized routes.

Verify these directories exist:

```text
storage/app
storage/app/private
storage/app/public
storage/framework/cache
storage/framework/cache/data
storage/framework/sessions
storage/framework/views
storage/logs
bootstrap/cache
```

The web/PHP user must be able to write `storage/` and `bootstrap/cache/`. Use the provider's normal ownership and `775`-style permissions where appropriate; never make the whole project `777`.

### When symbolic links are blocked

Some shared hosts block PHP-created symlinks. Ask the host to create the link or an equivalent Apache/Nginx alias from the document-root `/storage` URL to `storage/app/public`. Do not create a public copy that silently becomes stale, and do not expose the entire application `storage/` directory. If the host cannot provide a safe alias, treat public uploads as a hosting blocker and ask the provider for a supported Laravel storage configuration before going live.

## 9. Cache, Sessions and Queues

### Cache

The project default is the database cache store, which is compatible with shared hosting. The cache migration is included. Configure `.env` before building the configuration cache. Redis is optional and should not be introduced unless the host provides it and the application is intentionally switched to it.

The application caches public site settings/chrome and short-lived dashboard metrics. Settings, navigation, business-unit and social-link changes clear the relevant cache. Dashboard metrics are intentionally cached for 30 seconds.

### Sessions

The production default is the database session driver. The sessions table is created by the first Laravel migration. Confirm that the table exists and that HTTPS cookies are enabled with `SESSION_SECURE_COOKIE=true` after SSL is active.

If the host cannot use database sessions, set `SESSION_DRIVER=file` and ensure `storage/framework/sessions` is writable. Do not change the driver without clearing/rebuilding configuration.

### Queues

The default `QUEUE_CONNECTION=database` uses the included `jobs` and `failed_jobs` migrations. Payment-confirmation and waitlist messages implement `ShouldQueue`, so a worker is needed for delivery. A persistent server can run:

```bash
php artisan queue:work database --tries=3 --timeout=120
```

On cPanel without a persistent worker, use a cron job that exits when the queue is empty. Replace the PHP path and account path with values from the host:

```cron
* * * * * cd /home/USERNAME/mwanafunzi && /usr/local/bin/php artisan queue:work database --stop-when-empty --tries=3 --timeout=120 >> storage/logs/queue.log 2>&1
```

Avoid overlapping long-running cron workers. Monitor `failed_jobs` and use `php artisan queue:failed`/`php artisan queue:retry all` deliberately after reviewing failures.

### Scheduler

No Laravel scheduler task is currently defined. Do not add a scheduler cron for this release. If future code adds tasks, use the host's PHP path with:

```cron
* * * * * cd /home/USERNAME/mwanafunzi && /usr/local/bin/php artisan schedule:run >> /dev/null 2>&1
```

Before enabling paid production commerce, configure `PAYMENT_PROVIDER=flutterwave`, `PAYMENT_ENVIRONMENT=production`, the Flutterwave production keys and webhook hash, then test the provider's return and webhook URLs over HTTPS. Do not use sandbox credentials or the deterministic sandbox checkout in live commerce.

## 11. HTTPS / SSL

1. Connect the domain DNS to the host.
2. Issue a certificate through cPanel AutoSSL or the provider's supported certificate service.
3. Set `APP_URL` to the HTTPS domain and `SESSION_SECURE_COOKIE=true`.
4. Confirm the hosting panel's HTTP-to-HTTPS redirect does not conflict with application/proxy redirects.
5. Verify login, CSRF-protected forms, uploads and payment return URLs over HTTPS.

Do not enable `SESSION_SECURE_COOKIE=true` before HTTPS is actually working on the live domain, or login cookies will not be sent over HTTP during setup.

## 12. SEO and Public URLs

Public absolute URLs are generated with Laravel `route()`, `url()`, `asset()` and the configured `APP_URL`. Set the final domain before caching config. Do not hardcode a local URL in CMS SEO fields.

The application provides:

- `GET /sitemap.xml`, containing homepage, business routes, published learning topics, published courses, available products, published articles, active services, published projects and intended public pages.
- `GET /robots.txt`, generated by Laravel with an absolute sitemap URL based on the live request/configured application URL. It allows crawling by default and does not contain `Disallow: /`.
- Canonical, Open Graph and structured metadata for public pages, services and projects.
- No admin, draft or unpublished service/project URLs in the sitemap.

After deployment, inspect the rendered HTML and submit the sitemap in the search engine webmaster tools for the final domain.

## 13. Security and Error Handling

- Admin routes are behind `auth` and `admin` middleware; public users must not be able to access CMS actions.
- Login, contact, registration, waitlist and checkout writes have throttling where appropriate.
- POST/PUT/PATCH/DELETE forms use Laravel CSRF protection.
- Upload validation and signed/private download routes are enforced in application code.
- Admin passwords are created/updated through Laravel hashing and the password-prompting admin command.
- `APP_DEBUG=false` prevents exception details from being shown publicly.
- Never log passwords, API keys, SMTP passwords, payment secrets or session tokens.

Custom views exist for 403, 404, 419, 422, 429, 500 and 503. If an error still appears as a hosting-generated page, inspect the PHP/web-server logs and confirm the request reaches Laravel's `public/index.php`.

## 14. Backups and Deployment Safety

Before every major live deployment:

1. Export the database or create a verified hosting snapshot.
2. Back up `storage/app/public` and `storage/app/private` uploaded media/assets.
3. Back up the server `.env` securely, separately from the repository.
4. Build/test the release before uploading it.
5. Put the application in maintenance mode if the deployment changes schema or replaces many files.
6. Deploy code and dependencies.
7. Run incremental migrations.
8. Create the storage link and verify permissions.
9. Build/warm Laravel caches.
10. Verify the health endpoint, public routes, login, admin, uploads, contact flow and sitemap before reopening the site.

Database backups must be stored securely and tested for restoration. Media backups are separate from database backups. Never publish `.env` backups or include them in a public archive.

### Maintenance mode

When appropriate:

```bash
php artisan down --render="errors::503"
# deploy, migrate and verify
php artisan up
```

If a migration, dependency install or cache build fails, keep maintenance mode enabled until the failure is fixed or the previous release is restored.

### Minimizing downtime

Build frontend assets before the maintenance window, upload dependencies before switching the document root, use only incremental migrations, back up first, and warm config/route/view caches before bringing the site back up. A normal shared-hosting deployment does not require containers or Kubernetes.

If SSH/cPanel Terminal is unavailable:

1. On a compatible PHP 8.2+ build machine, run `composer install --no-dev --prefer-dist --optimize-autoloader`.
2. Run `npm ci && npm run build`.
3. Upload the application files, `vendor/`, and generated `public/build/` using the file manager/SFTP. Do not upload `.env` from development.

5. Import an initial database only when appropriate, or ask the host to run `php artisan migrate --force` through support. Never import a local development database over an existing production database.

7. Ask the provider to create the storage alias if symlinks are unavailable.
8. Set ownership/permissions for `storage/` and `bootstrap/cache/` through the provider's supported method.

## 19. Troubleshooting

### 500 Internal Server Error

Inspect `storage/logs/laravel.log` and the hosting PHP/web-server error log. Check `APP_KEY`, `.env` syntax, PHP version/extensions, database credentials, document root, ownership and `storage/`/`bootstrap/cache/` permissions. Confirm `APP_DEBUG=false` on public production responses.

### Vite manifest not found

Run `npm ci && npm run build`, then upload `public/build/` to the actual document root. Confirm that `public/build/manifest.json` exists and that the domain points at the intended `public` directory.

### Please provide a valid cache path

Create and make writable `storage/framework/cache/data`, `storage/framework/views`, `storage/framework/sessions` and `bootstrap/cache`. Run `php artisan optimize:clear` and rebuild config/view caches.

### Storage images are not loading

Check that `storage/app/public` exists, the public `/storage` link/alias points exactly there, the web user can read the files, and `APP_URL` is correct. Do not expose the whole `storage` directory.

### Database connection refused

Verify `DB_HOST`, `DB_PORT`, database name, username, password, MySQL privileges and whether the host requires a socket or a non-local database hostname. Run `php artisan migrate:status` from the application directory.

### 419 Page Expired

Check the session table/driver, writable session storage if using file sessions, `APP_URL`, HTTPS, `SESSION_SECURE_COOKIE`, domain/path cookies and server clock. Clear/rebuild configuration after changing `.env`.

### Permission denied

Fix ownership and writable permissions for `storage/` and `bootstrap/cache/` using the host's supported method. Do not make the full application or `public_html` world-writable.

### Blank or unstyled page

Check the Vite manifest, asset URLs, document root, `.htaccess`/Nginx rewrite rules, browser network errors and whether the build directory was uploaded. Do not run `npm run dev` as a production fix.

### Queued mail is not sent

Check `QUEUE_CONNECTION`, the `jobs`/`failed_jobs` tables, SMTP values, `storage/logs/laravel.log` and the queue worker/cron. Run a controlled `php artisan queue:work database --stop-when-empty --tries=3` test.

## 20. Rollback Procedure

1. Put the site in maintenance mode if necessary.
2. Restore the previous code release or switch the document root back to the previous release.
3. Restore the previous `public/build` assets with the matching code release.
4. Restore media only if the deployment changed or deleted media files.
5. Clear and rebuild config, route and view caches.
6. Restore the database only when migration compatibility and the backup point require it. Do not overwrite newer orders, payments, enquiries or user data casually.
7. Verify `/health`, login, admin, public pages and queues before reopening the site.

## 21. Production Logging and Rotation

Set production logging to a daily channel where possible:

```dotenv
LOG_CHANNEL=stack
LOG_STACK=daily
LOG_LEVEL=warning
LOG_DAILY_DAYS=14
```

Logs are stored under `storage/logs/laravel.log` (and rotated files for the daily channel). Keep the directory writable, monitor disk usage, and retain only the period required by the hosting/operational policy. Never include passwords, API secrets, payment details or session tokens in log messages.

## 22. Final Audit Notes

- `env()` calls are confined to configuration files; application code reads runtime configuration through `config()`.
- No runtime code depends on `C:\xampp`, `htdocs`, a Windows absolute path, `php artisan serve`, `127.0.0.1` or a local IP. Localhost values in framework/config defaults and `.env.example` are development defaults only; production must provide every URL/host value in `.env`.
- No committed `.env`, generated log, SQL dump, private key or real credential was found in the audited repository. Test fixtures and the local-only demo seeder account are not production credentials; the production seeder guard prevents that demo account from being created when `APP_ENV=production`.
- No scheduler task is currently registered.
- The main queued work is commerce/waitlist mail, using the database queue.
- The admin search intentionally uses simple `LIKE` queries suitable for the current CMS scale; introduce a search service only if the content volume makes that necessary.
